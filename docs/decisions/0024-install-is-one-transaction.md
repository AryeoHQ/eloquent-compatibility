# 0024. Install is one transaction

## Context

Install ran in three phases: statements committed before the lock, the locked transaction, and work after the commit. The retained primary key was added after the commit. When that step ran out of retries, the view was live, and no operation could finish the key.

Under the lock, install scanned whole tables to prove its invariants. `lock_timeout` bounded only the wait to acquire a lock, not the time install held it. A dependent view failed install late with `2BP01`, or followed the rename and silently omitted successor-created rows. Aryeo built its own capture and replay of dependent views around the package, with durable checkpoints.

## Decision

With legacy identity on the legacy table, install needs no foreign key repointing, no generated column, no install-time key and no step after the commit. Its locked phase runs in one transaction.

- Before the lock, install runs passes until one changes the outcome of fewer rows than its pass size. A row walked and left as it was does not count, so a pass that changes no row always stops the loop, and the gate then refuses on refused or failed rows. This amends the earlier design, which counted the rows a pass walked, so that NULL timestamps and refused rows kept install from its proofs. Install then records the start time of its read of native roots. It reads the keys of member roots without a legacy row through the indexed anti-join on the successor key, excluding a root that a `deleted` ledger row names. It writes nothing for them, and reports their count.
- Whole-table proofs, of existence and of values, run before the lock. They read only. The existence proof checks that every non-NULL successor key names an existing root row, whatever the row's ledger state. It reads the root's table without global scopes, so a trashed root exists. Install catches up the keys the existence proof and the value proof flag, proves them again, and refuses only when they still fail. This amends the earlier design, which refused on any difference. Declined: refusing on the first difference, which blocks install forever on a write that leaves `updated_at` alone.
- Under the lock, install runs only the final small catch-up, one indexed probe for a NULL successor key, the rename, the drop of mapped columns, the insert of one retained row per natively created root, the `NOT VALID` check that keeps the key non-NULL, the view, the dependent hooks and, as its last statement, the successor key's `NOT VALID` foreign key to the root. That statement runs under `SET LOCAL lock_timeout`, and install retries on a lock timeout or `40P01`, because its lock waits for every open writer of the root's table. Install never validates the foreign key: the existence proof before the lock checks that each key's root row exists ([0018](0018-legacy-identity-stays-on-the-legacy-table.md)). The native-root insert covers the keys the pre-lock read found, plus every member root whose `created_at` is at or after that read's start time minus the margin. It anti-joins both against the retained table's successor key, so a root the final pass just created is excluded, and it excludes a root that a `deleted` ledger row names. It runs the legacy initializer per row, with the Backfill origin, and catches nothing from it: a refusal aborts install and names the key and the reason. This amends the earlier design, which inserted for every member root created since the read, and so failed with `23505` on a root the final pass had just created.
- The final catch-up calls no write scope and runs no key re-check. The table lock serializes it against live writes.
- `compatibility:sql install` prints each lock with its mode and table. A required statement timeout argument sets `statement_timeout` for every statement under the lock, and is also the total budget for the hold. Install checks the time elapsed since it took the lock before every step under the lock, and before every native-root insert. Once the budget is spent, it rolls back and refuses, naming the step it reached. The package has no configuration of its own. Declined: a per-statement timeout only, because nothing would then bound the hold, and PostgreSQL 14 has no `transaction_timeout`.
- Prepare, install, rollback and `compatibility:sql` list every object that depends on the legacy table. Install refuses before any work when one exists and the map declares no `dependents()`.
- The dependents class runs inside the install transaction, through beforeInstall() and afterInstall(), and mirrors both for rollback through beforeRollback() and afterRollback().
- Install refuses when `<legacy>_backfill` is missing, and the refusal names `prepare()`. Install deletes the model's `compatibility_backfills` row, its watermark. A re-install after a rollback therefore runs `prepare()` again, which inserts that row, then passes, then install.
- The package has no public state() method. `compatibility:status` prints each legacy model's stage from the catalog and the ledger, with the pass count, the watermark and the refused and failed counts of a backfilling model, and `prepare()`, `install()` and `rollback()` are idempotent.
- The writer boundary is documented, not enforced. After install, a raw write to the legacy name fails loudly with a database error, and so does a model class from before the release. Eloquent writes through the legacy model and `toBase()` writes are translated, and reads keep working.

Declined: package-managed rebinding of dependent views, until a second adopter needs plain rebinds. Also declined: inserting native roots' rows before the lock with the mapped columns filled from the successors, because the final pass would overwrite a v2 edit made inside the install window. Also declined: a free-form status, and proofs that record flagged keys as failed in the ledger, because those marks roll back with a refusal inside a caller's transaction.

## Consequences

- A refusal under the lock commits nothing from the locked phase. The passes, the catch-up of flagged keys and the deletions before the lock commit as a pass does: each chunk, or each row for a scoped map ([0023](0023-the-backfill-records-an-outcome-per-row.md)). A later refusal keeps them. A retry therefore starts from the state those passes left. Inside a caller's transaction, a refusal loses nothing, because the next install flags the same keys again.
- Install deletes no ledger row, so the time it holds its locks does not grow with the ledger.
- Legacy readers do not see a successor created natively before install until install inserts its retained row. No pass walks that row, and install's pause grows with the number of such roots, inside the statement timeout.
- The time install holds its locks does not grow with the legacy table's size. It grows with the final pass and with the number of native roots, and the budget caps it.
- The consumer decides what a dependent becomes after install, through its dependents class.
- The consumer searches for raw writes, and ships the trait-carrying model at least one release before install.
- [Lifecycle](../specification/lifecycle.md#install) states the steps.
