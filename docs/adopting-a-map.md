# Adopting a map

This page is for the pull request that adds a compatibility map to an application. It lists what changes for the application's code and tests once a model is mapped. Each section names the change, why it happens, and what the pull request does about it.

## Mark each mapped model

Every model a map names, the previous model and each current model, implements `Compatible` and uses `HasCompatibility`. The trait overrides `Model::setKeysForSaveQuery()` and `Model::getAttributesForInsert()`, and each override calls its parent first. Laravel calls them only inside the model's own write method, so the event bridge can tell the model's own statement from a listener's. The trait also overrides `Model::fireModelEvent()`, so the bridge sees every model event of the model, whatever its listeners return. [Decision 0023](decisions/0023-a-mapped-model-marks-its-own-statement.md) records why the mark lives on the model.

Two kinds of model cannot carry the mark:

- **A model that declares any of the three methods itself**, takes one from another trait, or extends a class that does. PHP prefers the class's method to the trait's, so the statement goes unmarked, or the bridge never sees the model's events. `EventBridge::mirror()` refuses such a model with `InvalidCompatibilityMap`. Before that, the `HasCompatibilityMustNotRedeclareWriteHooks` PHPStan rule reports a named class whose method resolves anywhere but `HasCompatibility`. A composite-key package that sets the save query's keys is one example.
- **A model whose own write method sends its statement through neither method**, such as an override of `performUpdate()` that builds its own query. The bridge cannot see that at registration. The write's created, updated or deleted event throws `CompatibilityEventMirrorBypassed`, which names the model and the event. Inside a transaction, the throw rolls the write back. Outside one, the write has already committed.

[INV-50](invariants.md) records the rule.

## Before the install: views on the old table

A view on the old table follows the table's rename, so it keeps reading the retained table. It then misses every mapped attribute, and the triggers never see its writes. `Installer::install()` refuses while another view or materialized view reads the retained table, and names each one. [INV-42](invariants.md) records the rule.

Redirect each such view in the migration that installs the map:

1. Drop the view after the rename, and before `Installer::install()`.
2. Install the map.
3. Create the view again over the compatibility view, which now has the old table's name.

A view over the compatibility view blocks a later recompile in the same way. `Installer::recompile()` drops the compatibility view and creates it again, so it refuses while another object depends on it. A migration that recompiles drops those objects first and creates them again after. [INV-41](invariants.md) records that rule.

## What the install refuses

The install checks the tables before it changes anything, and each refusal is an `InvalidCompatibilityMap`:

- **Row-level security.** The view and its `SECURITY DEFINER` triggers would bypass the table's policies, so a table with row-level security cannot be mapped yet. See [INV-38](invariants.md).
- **A required column nothing fills.** Every `NOT NULL` column without a default needs a value on each insert path. Fill a retained column with `PreviousModel::fillWhenCreatedFromCurrent()`, and a current column with an attribute or `PrimaryCurrentModel::fillWhenCreatedFromPrevious()`. See [INV-39](invariants.md).
- **A writable attribute on a generated column.** The database rejects every write to a generated column and to a `GENERATED ALWAYS` identity column. Declare such an attribute read-only with `Attribute::readOnlyBecause()`, and the insert leaves it out. A `GENERATED BY DEFAULT` identity stays writable, and an insert through the view that omits it takes the identity's next value. See [INV-45](invariants.md).
- **A table outside the installation schema.** The compiled functions run in `current_schema()`, so every mapped table must be there. A table found only further down the search path refuses with "does not exist". Run the migration with that schema first on the search path. See [INV-47](invariants.md).
- **A Parental model.** `EventBridge::mirror()` refuses a class that uses Parental's HasChildren trait, because its children fire their events under their own class names. See [INV-43](invariants.md).
- **A model without the mark.** `EventBridge::mirror()` refuses a model that lacks `Compatible` or `HasCompatibility`, or that declares its own `setKeysForSaveQuery()` or `getAttributesForInsert()`. See [mark each mapped model](#mark-each-mapped-model).

## After the install: backfill the designations

A dependent declared with `DependentCurrentModel::designatedBy()` reads only the row its designation names. The designate trigger fills an empty designation when an insert or an update makes a dependent row readable. A record that exists before the install gets no such write, so its designation stays empty.

In the migration that installs the map, fill each empty designation with the row the view would read: the first readable row by key. `compatibility:check` reports every empty designation whose record has a readable row. [INV-12](invariants.md) records the rule.

## Guard each column trigger on a mapped column

PostgreSQL fires an `UPDATE OF <column>` trigger whenever the statement's `SET` list names its column, whether or not the value changed. The view's update trigger assigns every mapped column of each current table it writes and every written column of the retained table, and an unchanged column gets its own stored value. So an update through the view that changes only `title` fires an `UPDATE OF price_cents` trigger on `gadgets`. A trigger that audits price writes then records a write that never changed the price, and a trigger that refuses price writes refuses it. The event bridge compares rows, so its events are unaffected. [INV-7](invariants.md) records the rule.

`compatibility:check` warns of each `UPDATE OF` trigger on a current table or the retained table that names a column the update trigger writes and has no `WHEN` clause. The warning names the trigger, its table and its mapped columns, and the command's exit status stays the same. A trigger with any `WHEN` clause counts as guarded. The check skips internal triggers and every `compatibility__` trigger a map installs.

Guard each trigger with `WHEN (OLD.<column> IS DISTINCT FROM NEW.<column>)`, one comparison for each column it names, joined with `OR`. An `INSERT OR UPDATE OF` trigger cannot take that clause, because the `WHEN` clause of an insert trigger cannot reference `OLD`. Split it into an insert trigger and a guarded update trigger. This migration splits an `AFTER INSERT OR UPDATE OF price_cents` trigger on `gadgets`:

```php
<?php

use Illuminate\Database\Migrations\Migration;
use Illuminate\Support\Facades\DB;

return new class extends Migration
{
    public function up(): void
    {
        DB::unprepared(<<<'SQL'
            DROP TRIGGER audit_price ON gadgets;
            CREATE TRIGGER audit_price_insert AFTER INSERT ON gadgets
                FOR EACH ROW EXECUTE FUNCTION audit_price();
            CREATE TRIGGER audit_price_update AFTER UPDATE OF price_cents ON gadgets
                FOR EACH ROW WHEN (OLD.price_cents IS DISTINCT FROM NEW.price_cents) EXECUTE FUNCTION audit_price();
            SQL);
    }

    public function down(): void
    {
        DB::unprepared(<<<'SQL'
            DROP TRIGGER audit_price_update ON gadgets;
            DROP TRIGGER audit_price_insert ON gadgets;
            CREATE TRIGGER audit_price AFTER INSERT OR UPDATE OF price_cents ON gadgets
                FOR EACH ROW EXECUTE FUNCTION audit_price();
            SQL);
    }
};
```

The column list of `INSERT OR UPDATE OF` limits only the update, so the insert trigger still fires on every insert, as the original did.

## Nullable columns keep no default on an insert

An insert through the view writes every column an attribute stores. When the insert omits the attribute, a `NOT NULL` column with a default takes its default. A nullable column stores NULL instead, even when it has a default. That holds for a dependent's column and for a `writesTo()` target. A retained or primary column that an attribute stores through `Attribute::storedAs()` takes the column's default as its view default. [INV-46](invariants.md) records the rule.

## Tests that fake every event

Once a model is mapped, a test that writes it under `Event::fake()` or `Event::fakeExcept()` throws `CompatibilityEventMirrorBypassed`. The throw comes before the statement, so the write never reaches the database. The fake swallows the beginning event, so no listener runs, the bridge forgets the write it began, and the test proves nothing about the other side. The guard stays on by default, because it is what stops silently lost mirrored events. [INV-21](invariants.md) records it.

The pull request that adds each map moves every test it touches to one of two forms:

- `Event::fake()` given a list of only the events the test asserts, which leaves the model events alone.
- `EventBridge::withoutMirroring()` around the write, or `InteractsWithCompatibilityMaps::withoutEventMirroring()` in a test, which switches the mirror off on purpose.

## Tests at transaction level 0

`Illuminate\Foundation\Testing\RefreshDatabase` wraps each test in a transaction. Inside it, the bridge always works in savepoint mode, so a suite that uses only that trait never runs the level-0 path. That path opens the bridge's own transaction, commits it, and releases it after a failed statement. Production web requests and queue jobs usually take it.

Add a test class per map that uses `Illuminate\Foundation\Testing\DatabaseTruncation`, or that turns off the test transaction, and write through both sides outside a transaction. `EventBridgeOutsideTransactionTest` in this package shows the shape: its `connectionsToTransact()` returns no connection.

## A lost connection is not retried at level 0

At transaction level 0, Laravel reconnects and retries a statement once when the connection drops. The bridge opens its own transaction when a mapped write's statement starts. The statement then runs at level 1, where `Connection::handleQueryException()` rethrows instead of retrying. A mapped write that used to survive a dropped connection now fails, and so do the bridge's own reads. A connection class that hands non-idempotent writes to that retry loses it for mapped writes. [0021](decisions/0021-a-mapped-write-at-level-0-gives-up-the-lost-connection-retry.md) records the trade-off.

## Jobs dispatched by mirrored listeners

At level 0, the bridge replays the other side's events before it commits its transaction, while it still holds the records' row locks. A queue connection with `after_commit` set to false pushes a job at once. A worker can then pick the job up before the row it reads has committed, and read the old row or wait on the lock.

Make each job a mirrored listener dispatches run after the commit: call `afterCommit()` on the dispatch, or implement `Illuminate\Contracts\Queue\ShouldQueueAfterCommit` on the job. Inside a caller's transaction, the job then waits for the caller's commit too.
